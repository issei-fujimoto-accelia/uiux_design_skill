# 変更の分類と手順

指摘は「層 × 操作」で分類し、共通の手順で直す。
具体的な変更の例を網羅することはせず、層で「どの文書を直し、影響がどこへ伝わるか」を、操作で「ID をどう扱うか」を決める。
間違えやすい組み合わせだけを、最後の「注意が要る組み合わせ」に挙げる。

## 層：どこを直すか

上ほど影響が広い。1つの指摘が複数の層にまたがる場合は、上の層から順に直す。

| 層 | 正の文書 | 影響が伝わる先 | 例 |
|---|---|---|---|
| 方針 | `UI_GUIDELINES.md` 1〜3節（品質方針、ペルソナ、コンセプト） | すべて | 対象ユーザーを変える、与えたい印象を変える |
| 規則 | 画面をまたぐ `UI-N`（`UI_GUIDELINES.md` 4、6、8、9節、`UX_STRUCTURE.md` 4節） | その規則を適用した画面と部品（`data-rules`、詳細設計の「規則」列） | 主要操作の位置、本文の最小サイズ、用語の統一 |
| トークン | `design-tokens.json` | そのトークンを使う部品と画面 | 色、文字、余白、角丸、影、動き、モード（ダーク）、ブレークポイント |
| 導線 | `UX_STRUCTURE.md` 1〜3節（FLW、画面一覧、遷移）、ナビゲーションの規則 | 経由する画面、遷移でつながる画面 | 画面の追加・削除・分割・統合、順序、ナビゲーションの方式 |
| 部品 | `components/CMP-N.md`、`UI_GUIDELINES.md` 7節（一覧） | その部品を使う画面、その部品を中に含む部品、部品カタログ | 見た目、受け取る値、状態と変種、部品の分割・統合・廃止 |
| 画面 | `screens/SCR-N.md` | その画面（実装済みなら実装） | 領域、優先度、状態、操作、文言、画面独自の要素、プラットフォームの差 |

方針の層の変更は、このスキルでは直さない。design-foundation に戻るよう提案する。導線全体を組み直す変更は design-structure に戻る。

## 操作：何をするか

| 操作 | ID と名前の扱い |
|---|---|
| 追加 | 新しい番号を振る（最大値の次。欠番を再利用しない）。上流に由来しなければ、由来を `追加：<理由>` にし、「上流への反映」に挙げる |
| 変更 | ID はそのまま。`data-ui` の名前、部品の要素名、受け取る値の名前を変える場合は「削除と追加」として扱い、「実装への影響」に挙げる |
| 削除 | 行を消さず、名前に `（廃止）` を付けて残す。統合・置き換えなら、移動先の ID を理由に書く。廃止した ID への参照をすべて外す |
| 移動 | 持ち主を変える（共通部品 ⇔ 画面独自、部品の統合・分割、画面の統合・分割、領域を別の画面へ）。移動先に「追加」し、移動元を「削除」か参照の付け替えにする |

## 共通の手順

1. **分類する。** 指摘を「層 / 操作」に分け、ラウンドの記録に書く。複数にまたがる指摘は行を分ける。
2. **直す箇所を決める。** 層の表から、正の文書の該当箇所を決める。
3. **影響範囲を出す。** 変更する ID とトークンを指定して `impact.py` を実行し、記録に貼る。

   ```
   python3 scripts/impact.py --root <プロジェクト> --id <UI-N|FLW-N|SCR-N|CMP-N> --token <トークンのパス>
   ```

4. **文書を直す。** 操作の表に従って ID を扱う。上の層から、文書 → トークンの順に直す。
5. **関連する文書をそろえる。** 層ごとに、次の箇所がずれやすい。

   | 層 | そろえる箇所 |
   |---|---|
   | 規則 | 適用している画面・部品の「規則」列、モックの `data-rules` |
   | 導線 | FLW の手順と手数、遷移の図と表、各画面の「入口と出口」、部品の「使う画面」、照合の `routes`（使っている場合） |
   | 部品 | `UI_GUIDELINES.md` 7節の一覧と「使う画面」、各画面の領域の「部品」列、部品カタログ |
   | 画面 | ワイヤー、文言、状態の網羅、画面独自の要素 |

6. **モックを直す。** 文書と一致させる。
7. **確かめる。** ビルド、検査、前後の比較を行う。変化した画面と影響範囲を突き合わせる。影響範囲の外で変化した画面は意図しない変更、影響範囲の中で変化しない画面は直し漏れを疑う。

## 注意が要る組み合わせ

| 組み合わせ | 注意点 |
|---|---|
| 部品 / 移動（共通 → 画面独自） | 先に、変種の追加で済まないかを検討し、済まない理由を領域の「理由」列に書く。画面の詳細設計の「画面独自の要素」に構成と状態を書く。使う画面が1つ以下になった部品は、残すか廃止するかをユーザーに確認する |
| 部品 / 移動（画面独自 → 共通） | 構成と受け取る値が既存の部品とほぼ同じなら変種の追加（部品 / 変更）、大きく違えば新しい部品（部品 / 追加）にする。各画面の独自の要素を部品に置き換え、「画面独自の要素」から外す |
| 部品 / 移動（統合・分割） | 統合なら片方を廃止し、理由に統合先を書く。分割なら、各画面がどちらを使うかを領域の「部品」列で決め直す |
| 部品 / 変更（互換性がない） | 受け取る値の名前の変更・削除、変種の削除。使っている画面の属性をすべて直し、「実装への影響」に挙げる |
| 画面 / 変更（`data-ui` の名前） | 削除と追加として扱う。実装済みなら、実装の `data-ui` も直す必要がある |
| 導線 / 移動（画面の統合・分割） | 統合元の画面を廃止し、領域と状態を統合先に移す。分割は、新しい画面の追加と、元の画面の領域の削除として扱う |
| 導線 / 変更（ナビゲーションの方式） | 全画面が影響範囲になる。プラットフォームの慣習（`platforms.md`）から外れる場合は、理由を `UI-N` に書く |
| 規則 / 変更 | 規則を適用した全箇所が影響範囲になる。規則の文と、適用箇所の見た目の両方を直す |
| トークン / 追加（モード） | ダークモードなどを足す場合、すべての色にそのモードの値を持たせ、コントラストをモードごとに検査する |
| 方針 / 任意 | このスキルでは直さない。「上流への反映」に挙げ、design-foundation に戻るよう提案する |
